Chapter 8Permissions and Ownership

Every file has an owner, a group, and nine permission bits. Once the notation clicks, this stops being mysterious.

Reading the bits

-rwxr-xr--  1 dave  developers  4096 Aug 14 09:03 deploy.sh
 └─┬─┘└┬┘└┬┘    └─┬─┘  └───┬────┘
   │   │  │       │        └ group
   │   │  │       └ owner
   │   │  └ others: r-- (read only)
   │   └ group:   r-x (read, execute)
   └ owner:       rwx (read, write, execute)
BitOn a fileOn a directory
r (4)read its contentslist its contents
w (2)modify itcreate/delete files inside it
x (1)run it as a programenter it (cd) and access files inside

The directory column is the part people get wrong. You can delete a file you have no write permission on, provided you can write to the directory containing it — the permission that matters is on the directory entry, not the file. And a directory with r but no x lets you see names but not read anything inside.

chmod: changing permissions

Two notations, both worth knowing. Symbolic is readable and relative:

$ chmod +x script.sh          # make executable (for everyone, subject to umask)
$ chmod u+x script.sh         # executable by the owner only
$ chmod g-w file.txt          # remove write from the group
$ chmod o-rwx secret.txt      # others get nothing
$ chmod a+r public.txt        # everyone can read
$ chmod u=rw,go=r file.txt    # set exactly, don't add or subtract

Numeric is terse and absolute. Add the values: r=4, w=2, x=1.

NumberMeansTypical use
644rw-r--r--ordinary file: owner edits, everyone reads
755rwxr-xr-xscript or directory: everyone can run/enter
600rw-------private file: keys, credentials
700rwx------private directory
664rw-rw-r--shared with your group
777rwxrwxrwxalmost always a mistake
$ chmod 644 notes.txt
$ chmod 755 deploy.sh
$ chmod 600 ~/.ssh/id_ed25519      # ssh refuses to use a key with looser permissions
$ chmod -R 755 public_html/         # recursive
Two things to avoid

chmod 777 means anyone on the system can modify the file. It is almost never the actual fix for a permission problem; it is a way of not diagnosing one. And chmod -R 755 on a tree containing files will mark every data file executable — use find . -type d -exec chmod 755 {} + and find . -type f -exec chmod 644 {} + to treat directories and files differently.

chown: changing owner and group

$ sudo chown dave file.txt              # change owner
$ sudo chown dave:developers file.txt   # change owner and group
$ sudo chown :developers file.txt       # change group only
$ sudo chgrp developers file.txt        # same thing
$ sudo chown -R www-data:www-data /var/www/

Only root can give a file away to another user, which is why chown almost always needs sudo.

Who am I, really

$ whoami
dave
$ id
uid=1000(dave) gid=1000(dave) groups=1000(dave),27(sudo),999(docker)
$ groups
dave sudo docker

Group membership is evaluated at login. If someone adds you to a group, you will not have it until you log out and back in — a frequent source of "but I am in the docker group" confusion.

sudo

$ sudo systemctl restart nginx      # run one command as root
$ sudo -i                            # start an interactive root shell
$ sudo -u postgres psql              # run as some other user
$ sudo !!                            # rerun your last command with sudo

That last one is a history expansion — !! means "the previous command line" — and it is the single most-used trick in this book once you know it.

Prefer sudo cmd over sudo -i

A root shell has no seatbelt and no record of what you did in it. Running individual commands with sudo keeps each one logged and keeps your default state unprivileged, so a mistyped rm is merely annoying instead of fatal.

umask: default permissions

$ umask
0022
$ touch new.txt && ls -l new.txt
-rw-r--r--  1 dave  staff  0 Aug 14 09:30 new.txt

umask subtracts from the maximum default (666 for files, 777 for directories). With umask 022: 666 − 022 = 644 for a new file, 755 for a new directory. That is why new files are never executable by default — a sensible safety property.

Questions

Translate chmod 750 into words.

Owner 7 = 4+2+1 = read, write, execute. Group 5 = 4+1 = read and execute, no write. Others 0 = nothing at all. So: rwxr-x---. A common setting for a script that a team runs but outsiders should not even see the contents of.

You have read permission on a file but cannot open it. What is likely wrong?

You lack execute (x) permission on one of the directories in its path. To reach /a/b/c/file you need x on /a, /a/b, and /a/b/c — execute on a directory means "may traverse". Check with namei -l /a/b/c/file, which shows the permissions at every level of the path.

Why can you delete a file you do not own and have no write permission on?

Deleting removes a name from a directory, so the permission checked is w on the containing directory, not on the file. This is why /tmp has the "sticky bit" (drwxrwxrwt — note the t): it is world-writable, but the sticky bit restricts deletion to the file's owner. Without it, anyone could clear out everyone else's temp files.

Your script fails with "permission denied" even though you can read it. Two possible causes?

Either the file is not executable (chmod +x script.sh), or the filesystem it lives on is mounted noexec — common for /tmp on hardened systems. A third, sneakier cause: the shebang line points at an interpreter that does not exist, which some shells report as a confusingly similar error. As a workaround you can always run bash script.sh, which does not require the execute bit.

Why does ssh refuse your private key?

Because its permissions are too open. SSH requires the private key be readable only by you — chmod 600 ~/.ssh/id_ed25519 — and the ~/.ssh directory be 700. It refuses rather than warns, on the reasoning that a key other users can read is already compromised.
