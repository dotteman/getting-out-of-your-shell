Chapter 9Processes and Jobs

A process is a running program. The shell gives you tools to see them, control the ones you started, and stop the ones you did not.

Seeing what is running

$ ps aux                       # every process on the system
$ ps aux | grep nginx          # the ones you care about
$ ps -ef                       # the same information, different formatting
$ pgrep -a nginx               # PIDs and command lines, without the grep noise
$ top                          # live, sorted by CPU
$ htop                         # top, but pleasant (install separately)

The columns in ps aux that matter: PID (the number you need to kill it), %CPU and %MEM, STAT (R running, S sleeping, Z zombie, D uninterruptible), and COMMAND.

$ ps aux --sort=-%mem | head -n 6      # top 5 memory consumers
$ ps -o pid,ppid,cmd -p 4821            # specific fields for one PID

In top: M sorts by memory, P by CPU, k kills a PID, q quits, 1 shows per-core CPU.

Stopping processes

$ kill 4821                # polite: SIGTERM, asks it to shut down cleanly
$ kill -9 4821             # forceful: SIGKILL, cannot be caught or ignored
$ kill -HUP 4821           # SIGHUP: many daemons reload their config on this
$ pkill nginx              # kill by name
$ pkill -f "python app.py" # match against the full command line
$ killall firefox          # kill every process with that exact name

Always try kill before kill -9. SIGTERM lets a program flush its buffers, close database connections, and remove its lock file. SIGKILL removes it from the kernel's process table mid-sentence, and the cleanup becomes your problem.

SIGHUP1terminal closed; by convention, "reload your config"
SIGINT2what Ctrl-C sends
SIGKILL9die now, uncatchable

Job control: managing what you started

$ long_running_command &      # start it in the background
[1] 4821
$ jobs                         # list this shell's jobs
[1]+  Running    long_running_command &
$ fg %1                        # bring job 1 to the foreground
$ bg %1                        # resume a stopped job in the background
$ Ctrl-Z                       # suspend the foreground job
$ kill %1                      # kill by job number rather than PID

The everyday sequence: you start something, realize it will take ten minutes, press Ctrl-Z to suspend it, type bg to let it continue in the background, and get your prompt back. When it finishes, bash tells you.

Surviving a disconnect

Background jobs die when your shell exits, which matters over SSH.

$ nohup ./long_job.sh &             # ignore SIGHUP; output goes to nohup.out
$ nohup ./job.sh > job.log 2>&1 &   # ...with output where you want it
$ disown -h %1                       # detach a job you already started

For anything you will want to come back to, use a terminal multiplexer instead:

$ tmux new -s deploy      # start a named session
  (do work; press Ctrl-b then d to detach)
$ tmux ls                 # list sessions
$ tmux attach -t deploy   # reattach, from anywhere, later

tmux keeps a real terminal alive on the server. Your SSH connection dropping becomes a non-event rather than a lost deployment. If you administer remote machines, this is the highest-value thing in this chapter.

What is it doing?

$ uptime                    # load average: 1, 5, 15 minute
$ free -h                   # memory
$ df -h                     # disk space by filesystem
$ du -sh /var/log/*         # what is filling the disk
$ lsof -p 4821              # which files this process has open
$ lsof -i :8080             # which process is holding port 8080
$ ss -tulpn                 # all listening sockets and their processes
$ strace -p 4821            # every syscall it makes (loud, but decisive)

"Which process has port 8080?" is asked daily; lsof -i :8080 or ss -tulpn | grep 8080 answers it.

Load average

uptime's three numbers are the average number of processes wanting CPU over the last 1, 5, and 15 minutes. Compare them against your core count: a load of 4.0 on a 4-core machine is fully busy, on a 16-core machine it is idle. The trend across the three numbers tells you whether things are getting better or worse.

Questions

Why is kill -9 a last resort?

SIGKILL is handled by the kernel and never reaches the program, so it gets no chance to run cleanup code: buffers are not flushed (data loss), temp files and lock files are left behind, child processes can be orphaned, and databases may need recovery on restart. Send SIGTERM, wait a few seconds, and only escalate if the process ignores it. A process that ignores SIGTERM repeatedly is usually stuck in uninterruptible I/O (state D), where even SIGKILL will not help until the I/O completes.

What is the difference between &, nohup, and tmux?

& backgrounds a job within your current shell — it dies when the shell exits. nohup makes it ignore the hangup signal so it survives your logout, but you cannot interact with it again. tmux keeps an entire terminal session alive on the machine, so you can detach, disconnect, reconnect from a different computer, and pick up exactly where you left off, with scrollback and multiple windows intact.

You pressed Ctrl-Z and your program stopped. Is it still running?

No — it is suspended, not running and not consuming CPU. It sits in state T holding its memory. fg resumes it in the foreground, bg resumes it in the background. Forgetting a suspended job and closing the terminal will usually kill it, which is why bash warns "there are stopped jobs" when you try to exit.

How do you find what is holding port 5432?

sudo lsof -i :5432 or sudo ss -tulpn | grep 5432. Both need root to show processes owned by other users — without sudo you will see the port is in use but not by whom, which is the confusing half-answer people usually get.

Your disk is full. What are the first two commands you run?

df -h to find which filesystem is full, then du -sh /path/* | sort -h on that filesystem to walk down toward the culprit, repeating a level at a time. One catch: if df shows full but du does not account for it, a deleted file is still held open by a running process — lsof | grep deleted finds it, and restarting that process releases the space.
