Chapter 10The Environment and Quoting

Two topics that look unrelated but are the same subject: what the shell knows, and what the shell does to your text before running it.

Variables

$ name="Dave"              # no spaces around the = sign. None.
$ echo "$name"
Dave
$ echo "${name}s laptop"   # braces disambiguate where the name ends
$ unset name

A variable set this way is local to your shell. export makes it part of the environment, which means child processes inherit it:

$ export API_URL="https://api.example.com"
$ printenv API_URL
$ env | sort | less              # everything currently exported
$ API_KEY=secret ./script.sh     # set it for one command only

PATH

$ echo $PATH
/usr/local/bin:/usr/bin:/bin:/usr/sbin
$ which python3
/usr/bin/python3
$ export PATH="$HOME/bin:$PATH"    # prepend, so your version wins

When you type python3, bash walks PATH left to right and runs the first match. This explains two everyday mysteries: "command not found" for a program you know is installed (its directory is not in PATH), and "why is it running the wrong version" (an earlier PATH entry wins).

Never put . in your PATH

If the current directory is searched for commands, then cd-ing into a directory someone else can write to and typing ls may run their ls. This is why running a script in the current directory requires the explicit ./script.sh.

Quoting: the rules that cause the most bugs

FormBehavior
'single'everything is literal. No expansion of any kind.
"double"expands $variables, $(commands), and backslashes; protects spaces and globs.
no quotesexpands everything, and splits on whitespace, and expands globs.
$ file="my report.txt"
$ ls $file          # ls sees TWO arguments: "my" and "report.txt" — fails
$ ls "$file"        # ls sees one argument — works
$ echo '$HOME'
$HOME
$ echo "$HOME"
/home/dave

The rule that will serve you for years: double-quote every variable expansion unless you have a specific reason not to. Filenames with spaces, empty variables, and values containing * all break unquoted code, and they break at the worst possible moment.

$ rm $file          # if file="" this becomes bare `rm` — harmless
$ rm -rf $dir/*     # if dir="" this becomes `rm -rf /*` — catastrophic
$ rm -rf "$dir"/*   # if dir="" this errors out safely

What bash does before running your command

Understanding the order removes most surprises. Bash processes a line roughly like this:

  1. Brace expansion — {a,b} becomes a b
  2. Tilde expansion — ~ becomes /home/dave
  3. Parameter expansion — $VAR becomes its value
  4. Command substitution — $(cmd) becomes cmd's output
  5. Word splitting — unquoted results split on whitespace
  6. Glob expansion — *.txt becomes the matching filenames
  7. Redirection is set up, then the command finally runs

Two consequences you will meet in practice. First, a variable's value is re-split and glob-expanded at step 5 and 6 — which is exactly why quoting matters. Second, redirection happens last, in your shell, which is why sudo cmd > /root/file fails (Chapter 5).

Parameter expansion tricks

$ f="report.tar.gz"
$ echo "${f%.gz}"        # strip shortest match from the END   -> report.tar
$ echo "${f%%.*}"        # strip longest match from the END    -> report
$ echo "${f#report.}"    # strip shortest from the START       -> tar.gz
$ echo "${#f}"           # length                              -> 14
$ echo "${f/tar/TAR}"    # replace first occurrence
$ echo "${name:-guest}"  # use "guest" if name is unset or empty
$ echo "${name:?must be set}"   # abort with a message if unset

These avoid spawning basename, sed, or cut for trivial string surgery, which matters inside loops.

Making it stick: .bashrc

Settings typed at the prompt vanish when you close the terminal. To make them permanent, put them in ~/.bashrc.

# ~/.bashrc

export EDITOR=vim
export PATH="$HOME/bin:$PATH"

alias ll='ls -lah'
alias ..='cd ..'
alias gs='git status'
alias grep='grep --color=auto'

# a function, for when an alias isn't enough
mkcd() { mkdir -p "$1" && cd "$1"; }

# bigger history, no duplicates, appended not overwritten
HISTSIZE=50000
HISTFILESIZE=50000
HISTCONTROL=ignoreboth:erasedups
shopt -s histappend
$ source ~/.bashrc      # apply without opening a new terminal
$ . ~/.bashrc           # same thing, shorter

~/.bashrc runs for every interactive non-login shell — new terminal windows. ~/.bash_profile runs for login shells (SSH sessions, console logins). The conventional fix is to have .bash_profile source .bashrc so you only maintain one file. On macOS with zsh, the equivalent file is ~/.zshrc.

History

$ history | tail -n 20
$ history | grep docker      # what was that command last week?
$ !!                          # last command
$ sudo !!                     # last command, with sudo
$ !342                        # command number 342
$ !ssh                        # most recent command starting with ssh
$ !$                          # last argument of the previous command
$ Ctrl-R                      # interactive reverse search — type a few chars

Ctrl-R is the one to build a habit around. Press it, type any fragment of a command you ran before, press Ctrl-R again to cycle further back, Enter to run or → to edit. It replaces most of what people use ↑ for.

Questions

Why does name = "Dave" fail?

Bash splits on whitespace, so it reads name as a command and = and "Dave" as its arguments — hence "name: command not found". Assignment requires no spaces: name="Dave". This is unlike essentially every programming language, and it catches everyone once.

What is the difference between setting a variable and exporting it?

A plain assignment lives only in the current shell. export puts it in the environment, which is copied into every child process the shell spawns. So a script you run cannot see FOO=bar but can see export FOO=bar. Note that the flow is one-way: a child can never modify its parent's environment, which is why a script cannot change your working directory unless you source it.

When is it correct to leave a variable unquoted?

Rarely, and always deliberately: when you actually want word splitting — for example FLAGS="-v -x"; cmd $FLAGS to pass two separate flags. Even then, a bash array (flags=(-v -x); cmd "${flags[@]}") is the more robust construction. Inside [[ ]], bash suppresses splitting, so quoting is optional there — but quoting anyway costs nothing.

You added a directory to PATH in .bashrc but the command still is not found in your open terminal. Why?

.bashrc is read when a shell starts. Existing shells never re-read it. Run source ~/.bashrc in the open terminal, or open a new one. If it still fails, check with echo $PATH that the export actually took, and with ls -l that the target file is executable.

What does ${VAR:-default} do, and how is it different from ${VAR:?message}?

${VAR:-default} substitutes default when VAR is unset or empty, leaving VAR itself unchanged — it is how you give a script an optional argument. ${VAR:?message} instead prints the message to stderr and exits with an error when VAR is unset or empty — it is how you declare a required argument in one line. Both are worth committing to memory.

Why is rm -rf "$dir"/* safer than rm -rf $dir/*?

If $dir is empty or unset, the unquoted version collapses to rm -rf /* — the shell removes the empty word entirely, leaving a leading slash. The quoted version expands to rm -rf ""/*, which is not a valid path and fails harmlessly. Add set -u to your scripts and the unset case becomes an error before it ever reaches rm.
