Chapter 11Writing Scripts

A shell script is a file containing the commands you would have typed. That is the whole concept — but a few conventions separate a script that works today from one that works in six months on someone else's machine.

Your first script

#!/usr/bin/env bash
set -euo pipefail

echo "Hello from $0"
echo "Running as $(whoami) on $(hostname)"
$ chmod +x hello.sh
$ ./hello.sh

Two lines of boilerplate, both worth understanding:

The shebang #!/usr/bin/env bash tells the kernel which interpreter to use. Using env finds bash wherever it lives, which matters because it is /bin/bash on Linux and often /opt/homebrew/bin/bash on a Mac. Writing #!/bin/sh instead means a stricter POSIX shell where bash-isms like [[ ]] and arrays are unavailable.

set -euo pipefail is the single highest-value line in shell scripting:

  • -e — exit immediately if any command fails, instead of ploughing ahead
  • -u — treat an unset variable as an error, instead of silently expanding to nothing
  • -o pipefail — a pipeline fails if any stage fails, not just the last one

Without it, cd /nonexistent; rm -rf * in a script does exactly what you fear. With it, the script stops at the cd.

Arguments

#!/usr/bin/env bash
set -euo pipefail

echo "script name : $0"
echo "first arg   : $1"
echo "all args    : $@"
echo "how many    : $#"

if [[ $# -lt 1 ]]; then
  echo "usage: $0 SOURCE [DEST]" >&2
  exit 1
fi

src="$1"
dest="${2:-./backup}"      # second argument is optional

Note >&2 on the usage message: errors belong on stderr so that someone piping your script's output does not get the error text mixed into their data. And exit 1 — a non-zero exit code is how your script tells &&, CI systems, and other scripts that it failed.

Conditionals

if [[ -f "$file" ]]; then
  echo "it's a regular file"
elif [[ -d "$file" ]]; then
  echo "it's a directory"
else
  echo "no such thing" >&2
  exit 1
fi

Use [[ ]] in bash, not the older [ ]: it does not split unquoted variables, supports && and || inside, and supports regex matching with =~.

String vs number comparison

== compares strings, -eq compares numbers. [[ "10" == "9" ]] is false and [[ 10 -gt 9 ]] is true, but [[ "10" > "9" ]] is false — because as strings, "1" sorts before "9". Mixing these up produces code that is right for single-digit inputs and wrong afterwards.

Any command can be a condition — the exit code is the test:

if grep -q ERROR app.log; then
  echo "errors found"
fi

if ! command -v docker >/dev/null 2>&1; then
  echo "docker is not installed" >&2
  exit 1
fi

Loops

for f in *.txt; do
  echo "processing $f"
  mv "$f" "processed_$f"
done

for i in {1..5}; do echo "attempt $i"; done

for host in web-01 web-02 db-01; do
  ssh "$host" 'uptime'
done

# read a file line by line — note the quoting and IFS
while IFS= read -r line; do
  echo "line: $line"
done < servers.txt

# loop until something succeeds
until curl -sf http://localhost:8080/health >/dev/null; do
  echo "waiting for service..."
  sleep 2
done

while IFS= read -r line is the correct incantation for reading a file line by line: IFS= stops leading and trailing whitespace being stripped, and -r stops backslashes being interpreted. Memorize it as a unit.

Do not loop over ls

for f in $(ls) breaks on any filename containing a space or a glob character. for f in * is both simpler and correct, because glob expansion produces properly separated words. For recursive work, use find -print0 with while IFS= read -r -d '' f.

case

case "$1" in
  start)   echo "starting..." ;;
  stop)    echo "stopping..." ;;
  restart) echo "restarting..." ;;
  *)       echo "usage: $0 {start|stop|restart}" >&2; exit 1 ;;
esac

Cleaner than a chain of elif when you are matching one variable against several literal values, and it supports globs in the patterns (*.txt)).

Functions

log() {
  echo "[$(date +%H:%M:%S)] $*" >&2
}

backup() {
  local src="$1"
  local dest="${2:-/backup}"
  mkdir -p "$dest"
  tar -czf "$dest/$(basename "$src")-$(date +%F).tar.gz" "$src"
}

log "starting backup"
backup /etc /backup
log "done"

Functions take arguments the same way scripts do: $1, $2, $@. Always declare variables inside functions with local — without it they are global, and a function that quietly overwrites the caller's $i is a genuinely nasty bug to track down.

Making it robust

#!/usr/bin/env bash
set -euo pipefail

# clean up on exit, however we exit
tmpdir=$(mktemp -d)
trap 'rm -rf "$tmpdir"' EXIT

# require an argument
target="${1:?usage: $0 TARGET}"

# check dependencies up front
for cmd in curl jq tar; do
  command -v "$cmd" >/dev/null || { echo "missing: $cmd" >&2; exit 1; }
done

echo "working in $tmpdir on $target"

trap ... EXIT runs the cleanup whether the script finishes, fails, or is interrupted — the shell equivalent of a finally block. Combined with mktemp -d, it means your script never leaves debris behind.

Two habits worth adopting immediately

Run shellcheck yourscript.sh before you trust any script. It catches unquoted variables, useless cats, and a dozen subtle bugs, and it explains each one. And run with bash -x script.sh when debugging — it prints every command with its variables expanded, which usually makes the problem obvious in seconds.

A complete example

#!/usr/bin/env bash
#
# rotate-logs.sh — compress logs older than N days, delete ones older than M
#
set -euo pipefail

LOG_DIR="${1:-/var/log/myapp}"
COMPRESS_AFTER_DAYS=7
DELETE_AFTER_DAYS=90

log() { echo "[$(date +'%F %T')] $*"; }

[[ -d "$LOG_DIR" ]] || { log "no such directory: $LOG_DIR"; exit 1; }

log "rotating logs in $LOG_DIR"

compressed=$(find "$LOG_DIR" -name '*.log' -type f \
               -mtime +"$COMPRESS_AFTER_DAYS" -print | wc -l)
find "$LOG_DIR" -name '*.log' -type f -mtime +"$COMPRESS_AFTER_DAYS" \
     -exec gzip {} +

deleted=$(find "$LOG_DIR" -name '*.log.gz' -type f \
            -mtime +"$DELETE_AFTER_DAYS" -print | wc -l)
find "$LOG_DIR" -name '*.log.gz' -type f -mtime +"$DELETE_AFTER_DAYS" -delete

log "compressed $compressed, deleted $deleted"

Questions

What does each letter in set -euo pipefail actually prevent?

-e prevents the script from continuing after a failed command — without it, a failed cd is followed cheerfully by the next line. -u prevents typo'd or unset variable names expanding to an empty string, which is the mechanism behind most catastrophic rm accidents. pipefail prevents false | true from reporting success, which otherwise hides failures in the middle of a pipeline. Together they turn silent wrong behavior into a loud stop.

Why #!/usr/bin/env bash rather than #!/bin/bash?

env looks bash up in PATH, so the script works on systems where bash is not at /bin/bash — macOS with Homebrew bash 5, BSDs, Nix. The tradeoff is that it uses whichever bash comes first in PATH, which in a security-sensitive context (a setuid script, a cron job with a controlled environment) may be an argument for the absolute path. For everyday scripts, env is the better default.

Why is for f in $(ls) wrong?

Command substitution output is subject to word splitting, so a file named my report.txt becomes two iterations, and a file named * gets glob-expanded into every filename in the directory. for f in * avoids both: glob expansion produces a properly delimited list regardless of what the names contain. The only wrinkle is that * stays literal if nothing matches, so guard with [[ -e "$f" ]] || continue when that matters.

What does local do and why does it matter?

It scopes a variable to the function. Without it every assignment is global, so a function using i as a loop counter will silently clobber the caller's i — and the bug shows up as wrong results rather than an error. Declare every variable in every function local unless you specifically intend to modify global state.

How do you make sure a temp directory is removed even if the script fails halfway?

tmpdir=$(mktemp -d) then trap 'rm -rf "$tmpdir"' EXIT. The EXIT trap fires on normal exit, on set -e aborts, and on SIGINT/SIGTERM, so cleanup happens on every path out of the script. Add other signals explicitly if you need to distinguish them: trap cleanup EXIT INT TERM.

Your script works when you run it but fails from cron. Most likely cause?

The environment. Cron runs with a minimal PATH (often just /usr/bin:/bin) and does not read your .bashrc, so commands you rely on are not found and variables you assume are unset. The fixes: use absolute paths for programs, set PATH explicitly at the top of the script, and never depend on the working directory — cd to where you mean to be. Redirecting output to a log file (>> /var/log/myjob.log 2>&1) is what lets you see the error at all.
