Chapter 5Pipes and Redirection

This is the chapter that turns a pile of commands into a toolkit. If you only properly learn one chapter, make it this one.

Every command has three streams

When a program runs, the shell hands it three channels:

StreamNumberDefault
stdin — input0your keyboard
stdout — normal output1your screen
stderr — error output2your screen

Errors go to a separate channel on purpose, so that when you redirect output to a file the errors still reach you instead of silently landing in the data.

Redirection: pointing a stream at a file

$ ls > files.txt            # stdout to a file, overwriting it
$ ls >> files.txt           # stdout appended to the file
$ ls /nope 2> errors.txt    # stderr to a file
$ ls /nope > out.txt 2>&1   # stdout to file, then stderr to wherever stdout goes
$ ls /nope &> all.txt       # bash shorthand for the same thing
$ command > /dev/null 2>&1  # discard everything; /dev/null is the bit bucket
$ sort < unsorted.txt       # feed a file in as stdin
Order matters

2>&1 > file is not the same as > file 2>&1. Read it right to left as a series of assignments: the first sends stderr to the current stdout (the terminal) and only then moves stdout to the file — so errors still hit your screen. Put the redirection first: > file 2>&1. Or just use &>.

Pipes: one command's output as the next one's input

The | character connects stdout of the left-hand command to stdin of the right-hand one. No temporary files, and both commands run at the same time.

$ ls -l | wc -l                      # how many entries in this directory
$ ps aux | grep nginx                 # find nginx processes
$ cat access.log | grep 404 | wc -l   # how many 404s (and one useless cat)
$ grep 404 access.log | wc -l         # better

A realistic pipeline reads like a sentence. This one answers "which IP addresses hit us most?":

$ cut -d' ' -f1 access.log | sort | uniq -c | sort -rn | head -n 10
  4821 10.0.0.14
  3390 10.0.0.7
   902 192.168.1.55

Step by step: take field 1 using space as the delimiter → sort so identical lines are adjacent → uniq -c collapses runs and prefixes a count → sort numerically, largest first → take the top ten. The sort | uniq -c | sort -rn sequence is such a common idiom that it is worth memorizing as a single unit.

Build pipelines one stage at a time

Do not write the whole thing and then debug it. Run cut -d' ' -f1 access.log | head, look at the output, then add | sort | uniq -c | head, look again. Adding | head at the end of an in-progress pipeline keeps the output readable while you work.

tee: a pipe with a tap

$ make 2>&1 | tee build.log            # watch the output AND save it
$ make 2>&1 | tee -a build.log         # append instead of overwrite
$ echo "net.ipv4.ip_forward=1" | sudo tee -a /etc/sysctl.conf

That last line solves a problem that trips up everyone: sudo echo x > /etc/file fails, because the redirection is performed by your shell (unprivileged) before sudo ever runs. tee is the program doing the writing, so sudo tee works.

xargs: turn input into arguments

Some commands read stdin (grep, sort, wc). Others only take arguments (rm, cp, mkdir). xargs bridges the two.

$ find . -name '*.tmp' | xargs rm            # delete every .tmp file
$ find . -name '*.log' -print0 | xargs -0 rm # safe with spaces in names
$ cat servers.txt | xargs -I{} ssh {} uptime # run a command per line
$ ls *.csv | xargs -n1 wc -l                 # one argument per invocation
$ find . -name '*.jpg' | xargs -P4 -I{} convert {} {}.png   # 4 in parallel

-print0/-0 pairs null bytes as separators instead of whitespace, which is the correct way to handle filenames containing spaces. Use it by default when piping find into xargs.

Chaining on success and failure

$ mkdir build && cd build      # run the second only if the first succeeded
$ ping -c1 host || echo "host is down"   # run the second only if the first failed
$ cd /tmp ; ls                  # run both regardless

Every command returns an exit code: 0 means success, anything else means failure. $? holds the last one.

$ grep -q ERROR app.log
$ echo $?
0                                # 0 = found it = success

&& is the single most valuable operator in this list. cd /some/dir && rm -rf * is dramatically safer than cd /some/dir; rm -rf *, because if the cd fails, the second version deletes the contents of whatever directory you happened to be in.

Command substitution

$ echo "Today is $(date +%F)"
Today is 2026-08-14
$ tar -czf "backup-$(date +%F).tar.gz" data/
$ kill $(pgrep -f myapp)
$ files=$(ls *.txt | wc -l)

$(...) runs the command inside and substitutes its output. You may also see backticks — `date` — in older scripts; they work but do not nest, so prefer $( ).

Questions

Why does sudo echo "text" >> /etc/hosts fail with "permission denied"?

Because your shell sets up the >> redirection before it runs sudo, and your shell is not root. The sudo only elevates echo, which is not the process opening the file. Fix it with echo "text" | sudo tee -a /etc/hosts, or sudo sh -c 'echo "text" >> /etc/hosts'.

What does 2>&1 mean, character by character?

2 is stderr, > is redirect, &1 means "to wherever file descriptor 1 currently points" — the ampersand distinguishes it from a file literally named 1. So: "send stderr to the same place stdout is going right now." Because it copies the current destination, position in the command line matters.

You want the ten largest files in a directory tree. Sketch the pipeline.

du -ah . | sort -rh | head -n 10. du -ah prints sizes for all files, sort -rh sorts human-readable sizes (so 2G beats 900M) in reverse, head trims. The -h flag on sort is the piece most people do not know about, and it is what makes this work.

When do you need xargs instead of a plain pipe?

When the receiving command reads its inputs from the command line rather than from stdin. rm, mkdir, cp, and echo ignore stdin entirely — ls | rm does nothing useful. xargs reads stdin and rebuilds it into arguments. Commands like grep, sort, wc, and sed read stdin natively, so no xargs needed.

What is the difference between cmd1 && cmd2 and cmd1 ; cmd2?

; runs cmd2 unconditionally. && runs it only if cmd1 exited 0. In anything that touches files, prefer &&: it makes the second command's precondition explicit, and it is the difference between a failed cd being harmless and being catastrophic.

How would you check whether a string appears in a file without printing anything?

grep -q PATTERN file. The -q flag suppresses output and exits as soon as it finds a match; you read the result from the exit code. That makes it the right thing to put inside an if: if grep -q ERROR app.log; then ... ; fi.
