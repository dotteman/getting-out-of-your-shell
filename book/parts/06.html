Chapter 6Finding Things

Two questions come up constantly: where is that file? and which file contains that text? The answers are find and grep.

find: locating files by their properties

find has an unusual syntax — find WHERE CONDITIONS ACTION — but you only need a handful of conditions.

$ find . -name "*.log"              # by name, case-sensitive, from here down
$ find . -iname "readme*"           # case-insensitive
$ find /etc -type f                 # files only (-type d for directories, l for links)
$ find . -size +100M                # bigger than 100 MB (+/- for more/less)
$ find . -mtime -7                  # modified in the last 7 days
$ find . -mtime +30                 # modified more than 30 days ago
$ find . -mmin -15                  # modified in the last 15 minutes
$ find . -user dave                 # owned by a user
$ find . -perm -u+x                 # executable by its owner
$ find . -maxdepth 2 -name "*.conf" # don't recurse forever

Combine conditions — they are ANDed by default:

$ find /var/log -type f -name "*.log" -size +10M -mtime +7
$ find . -name "*.tmp" -o -name "*.bak"     # -o is OR
$ find . -type f ! -name "*.md"             # ! negates

Doing something with what you found

$ find . -name "*.tmp" -delete
$ find . -name "*.log" -exec gzip {} \;      # run gzip once per file
$ find . -name "*.log" -exec rm {} +         # batch them into fewer invocations
$ find . -name "*.conf" -exec grep -l listen {} +
$ find . -name "*.sh" -print0 | xargs -0 chmod +x

{} is a placeholder for each filename. \; ends the command and runs it once per file; + packs as many filenames as fit into each invocation and is much faster on large sets.

Always look before you delete

Run the find without -delete first and read the list. find . -name "*.log " -delete — note the trailing space inside the quotes — matches nothing, but a typo the other direction can match far more than you intended.

Faster alternatives

$ locate nginx.conf        # instant, from a nightly-updated database
$ sudo updatedb            # refresh that database
$ which python3            # where is the executable I would run?
/usr/bin/python3
$ type -a python3          # every match, including aliases and functions
$ command -v docker        # the script-friendly version of `which`

locate is fast because it does not search the disk — it queries an index. That also means it will not know about a file you created five minutes ago.

grep: finding text inside files

$ grep ERROR app.log                 # lines containing ERROR
$ grep -i error app.log              # case-insensitive
$ grep -n ERROR app.log              # with line numbers
$ grep -r TODO src/                  # recursive through a directory
$ grep -c ERROR app.log              # just the count
$ grep -v DEBUG app.log              # invert: lines NOT matching
$ grep -l ERROR *.log                # just list which files matched
$ grep -w cat notes.txt              # whole word only, so "category" won't match
$ grep -A3 -B1 ERROR app.log         # 3 lines after, 1 before each match
$ grep -C2 ERROR app.log             # 2 lines of context on both sides

These flags are the whole 80%. -r, -i, -n, -v, and -C will cover almost everything you do.

$ grep -rn "TODO" --include="*.py" .        # only search Python files
$ grep -rn "password" --exclude-dir=.git .  # skip the git directory

Combining find and grep

$ find . -name "*.conf" | xargs grep -l "ssl"          # which configs mention ssl
$ find /var/log -mtime -1 -type f -exec grep -H "OOM" {} +   # yesterday's logs
$ grep -rn "deprecated" $(find . -name "*.js" -mtime -30)

Rule of thumb: use find when the file's properties matter (name, age, size, permissions), grep -r when only the content matters, and combine them when both do.

Worth installing

ripgrep (rg) is a drop-in grep -r replacement that is dramatically faster, respects .gitignore automatically, and needs no flags for the common case: rg TODO. Nothing in this book depends on it, but if you search code daily it is the single best quality-of-life install.

Questions

When would you use locate over find?

When you want a file by name, anywhere on the system, right now, and it has existed since at least last night. locate reads a prebuilt index so it returns instantly; find / walks the entire disk and can take minutes. Use find when you need current results or when you are filtering on size, age, ownership, or permissions — things the index does not track.

What is the difference between -exec cmd {} \; and -exec cmd {} +?

\; runs the command once per file — 5,000 files means 5,000 processes. + appends as many filenames as will fit onto a single command line, so the same job might take three invocations. Use + whenever the command accepts multiple files (most do). Use \; when the command takes exactly one file, or when you need {} to appear more than once.

grep -r ERROR . in a git repo is slow and full of noise. Two ways to fix it?

Either narrow it — grep -rn ERROR --include="*.py" --exclude-dir=.git . — or use rg ERROR, which skips .git and anything in .gitignore by default and is parallelized. For a one-off, the flags are fine; if you do this daily, install ripgrep.

How do you find files modified in the last 30 minutes?

find . -mmin -30. Note that -mtime counts in days and -mmin in minutes, and that the minus sign means "less than" (i.e. more recent). -mtime +30 means older than 30 days; -mtime -30 means within the last 30 days. Getting the sign backwards is the classic mistake.

You need every line that mentions "error" in any case, but not lines that also say "ignorable". How?

Chain two greps: grep -i error app.log | grep -v ignorable. Piping greps together is the normal way to build up include/exclude logic, and it is far more readable than trying to express the whole thing as one regex.
